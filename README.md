# Nバック課題アプリ — 第1段階

仕様書は [nback-spec.md](nback-spec.md)。この README は実装側の話だけ。

## 動かす

`index.html` を開くだけ。ビルドもサーバも要らない。

ローカルで確認するとき:

```bash
python -m http.server 8123
```

## スマホで使う（GitHub Pages）

1. github.com で `nback` という名前のリポジトリを新規作成（README などは追加しない）
2. このフォルダで `git remote add origin https://github.com/USERNAME/nback.git`
3. `git push -u origin main`
4. リポジトリの Settings → Pages → Source を「Deploy from a branch」、Branch を `main` / `(root)` にして Save
5. `https://USERNAME.github.io/nback/` を開き、共有メニューから「ホーム画面に追加」

ファイル参照はすべて相対パスなので、サブディレクトリ配信でもそのまま動く。

**https で配信すること。** Wake Lock（課題中に画面を消させない）と Service Worker は
保護されたコンテキストでしか動かないので、LAN の平文 http で配ると両方とも無効になる。

### ホーム画面とオフライン

- `manifest.webmanifest` — Android Chrome が独立したアプリとして扱うために要る。
  iOS は `apple-mobile-web-app-capable` のメタタグだけで全画面になる
- `icons/` — 3×3グリッドの1マスが光っている図。作り直すなら `python tools/make-icons.py`
  （PNG を直接書き出すので Pillow は要らない）
- `sw.js` — 一式をキャッシュして、電波がなくても起動できるようにする

**ファイルを更新したら `sw.js` の `VERSION` を1つ上げること。**
ブラウザは `sw.js` の中身が変わったときだけ更新処理を始めるので、
ここが同じままだと古いキャッシュが配られ続ける。
更新は「次に開いたとき」に反映される（課題の途中で差し替わらないようにしてある）。

## 着手前に決めたこと（仕様書の3項目）

1. **動作環境** — ブラウザ単体（HTML/JS、依存ライブラリなし）。GitHub Pages に置いてスマホから使う
2. **音声の出し方** — 第2段階では事前録音した音声ファイルを使う。Web Speech API は使わない。
   `js/modalities.js` に `audio-letter` を1つ登録すれば載る作りにしてある
3. **保存先** — ブラウザ内 localStorage。中身は仕様書どおり1行1ブロックの形なので、
   `.jsonl` として書き出し／読み込みできる（端末を移すときはこれを使う）

廃止した「提示後に入力」の記録は**消す**。更新版を初めて開いた端末で自動的に落ちる。

## 応答方式

2つある。設定画面で切り替える。

### リアルタイム判定（no-go）— `js/runner.js`

提示中に、N個前と一致したらボタンかスペースキーを押す。一致しないときは押さない。
ヒット / ミス / 誤警報 / 正棄却 の4分類で記録し、**ヒット率と誤警報率を必ず別々に**持つ。d′ も出す。

### 自分のペース — `js/paced.js`

刺激が1つ出る → N個前に出たものを入力 → 入力した瞬間に次が出る。タイマーなし。
最初の N 問は「覚えるだけ」で「次へ」ボタン。出題は N + 回答数。

**課題は1つの実行部を共有する。** 違うのは「何を出すか」と「どう答えさせるか」だけなので、
`TASKS` に1つ足せば課題が増える。進行・採点・記録・履歴の区画分けは共通。
実際 `paced-mixed` は提示を `modalities.js` の `mixed-number-position` に委譲し、
入力に `dualPad()` を足しただけで載った。

| task id | 出るもの | 入力 |
|---|---|---|
| `calc-arith` | 四則演算の式 | 0〜9 のテンキー |
| `paced-number` | 0〜9 の数字 | 0〜9 のテンキー |
| `paced-position` | 3×3グリッドの1マスが光る | 3×3グリッド（数字ボタンには置き換えない） |
| `paced-mixed` | 試行ごとに数字か位置か | 位置グリッド + 数字パッドを左右に並べる |

**課題IDはリアルタイムのモダリティIDと別にしてある。** 同じ「数字」でも
リアルタイムは1〜9、こちらは0〜9で記号集合が違う。同じIDにすると記録を後から読むときに取り違える。
位置課題と混合課題の**提示**だけは `modalities.js`（`visual-position` / `mixed-number-position`）に
委譲している（見た目は同じでよいので）。混合の記号は `N5`（数字の5）/ `P3`（位置の3）。

計算の式は**答えから逆算して**作る。だから割り算は必ず割り切れるし、答えは必ず一桁に収まる。
`candidates(answer, op, maxOperand)` が候補を返し、`makeProblem()` が演算子と項を選ぶ。
足し算だけは項が答えを超えないので必ず1つ以上作れる。他の演算子が作れないときの逃げ道になっている。

採点は `core.scoreAnswers()`。正解列と回答列を突き合わせるだけなので3課題で共通。
ヒット率・誤警報率・d′ は算出せず `null` を入れる。

**2桁の答えに広げるとき** — `settings.calcAnswerMax` を 99 に、`buildConfig()` の `answerDigits` を 2 にする。
`pushValue()` が桁を貯めてから確定する形になっており、項の上限も `answerMax` から決めている。
テストの「2桁への拡張余地」がこの経路を固定している。

### 廃止：提示後に入力

「すべて覚えて最後に全部答える」方式は削除した。**Nバックではなく記憶スパン課題だったため**
（詳しい経緯は [nback-spec.md](nback-spec.md)）。

**過去の記録も残さない。** `storage.js` の `load()` が `responseMode: "recall"` の記録を落として
保存し直す（更新版を初めて開いた時点で、その端末から消える）。`merge()` も同じく除くので、
古い `.jsonl` を読み込んでも戻らない。落とすのを入口1か所に寄せてあるので、
`history.js` は廃止した方式を一切知らない。

設定に残っていた `recall` / `calc` は `storage.js` の `migrateSettings()` が今の形に寄せる。

## モダリティ

| id | 内容 | 入力 |
|---|---|---|
| `visual-number` | 1〜9の数字を中央に表示 | 数字パッド（キー: 1〜9） |
| `visual-position` | 3×3グリッドのマスが光る。中央を除いた8マス | マスをタップ（キー: 1〜9 が読み順のマス） |
| `mixed-number-position` | 試行ごとに数字か位置かが切り替わる | 位置パッドと数字パッドを並べる |

（入力パッドは「提示後に入力」方式で使う。リアルタイム判定では一致ボタン1つだけ。）

混合モードの記号は `N5`（数字の5）と `P3`（位置の3）の2種類。一致は**種類と値の両方**が同じときだけ。
数字はグリッドの中央に出す（中央マスは位置刺激には使わないので取り違えない）。
入力ではどちらのパッドを押したかで種類も同時に決まるので、1タップで答えられる。
キーは数字が 1〜9、位置が Q W E / A S D / Z X C。

## 構成

刺激列の生成と提示・入力を分離してある。モダリティは設定値で、分岐ではない。

| ファイル | 役割 | DOM |
|---|---|---|
| `js/core.js` | 刺激列の生成、2方式の判定、d′、難易度の目安 | 触らない |
| `js/modalities.js` | 提示方法と入力方法の登録 | 触る |
| `js/runner.js` | リアルタイム判定を1ブロック回す。チャンネルの配列を受け取る | 触る |
| `js/paced.js` | 自分のペース方式。3課題の定義と共通の実行部 | 触る |
| `js/storage.js` | localStorage と JSON Lines | — |
| `js/history.js` | 履歴の集計とグラフ | 触る |
| `js/app.js` | 画面の組み立てと進行 | 触る |
| `sw.js` | オフライン用のキャッシュ | — |
| `manifest.webmanifest` | ホーム画面に追加したときの見え方 | — |

`core.js` はモダリティを知らない。記号の配列を受け取って記号の列を返すだけで、
それが数字なのかマスの位置なのか、数字と位置の混合なのか、読み上げる文字なのかには関与しない。

## 第2段階を足すとき

**音（audio-letter）** — `js/modalities.js` に1つ足す。判定側は触らない。

```js
M['audio-letter'] = {
  id: 'audio-letter', label: '音声 (子音)', kind: 'audio', defaultKey: 'L',
  alphabet: () => ['C','H','K','L','Q','R','S','T'],
  format: s => s,
  mount: () => ({ audio: new Audio() }),
  show: (h, sym) => { h.audio.src = 'audio/' + sym + '.mp3'; h.audio.play(); },
  hide: () => {},
  unmount: () => {},
  mountInput: (c, settings, onPick) => { /* 8個の文字ボタン */ }
};
```

そのうえで `app.js` の `buildSetup()` にある `.filter(m => m.kind === 'visual')` を外す。

**デュアル** — `app.js` の `buildConfig()` で `channels` を2要素にするだけ。

```js
channels: [
  { modalityId: 'visual-position', key: 'A' },
  { modalityId: 'audio-letter',    key: 'L' }
]
```

`runner.js` はすでにチャンネルごとに独立した列を作り、独立に判定している。
リアルタイム方式なら反応ボタンがチャンネル数だけ並び、提示後入力方式なら入力パッドが並ぶ。
記録も `record.channels[]` に per-channel で入る（単一のときは先頭が
トップレベルにも出るので、履歴画面の集計はチャンネル数に依存しない）。

**適応的難易度** — `core.suggestNextN()`（リアルタイム / Jaeggi の 3・5 規則）と
`core.suggestNextTrials()`（提示後入力 / 問題数の増減）が既にある。今は結果画面に目安を出すだけ。

## ひっかけ (lure)

全方式で設定でき、既定は OFF。`core.generateSequence` の `lure` / `lureRate` で扱う。

**ON は「許す」ではなく「置く」。** N±1 の位置に決まった割合（既定25%）で同じ記号を置く。
通常の位置では N±1 の一致を作らないので、生じるひっかけは意図的に置いたものだけになる。
OFF なら1件も生じない。ターゲットとは重ならず、ターゲット数も変わらない。

記録には `lure` / `lures` / `lurePositions` を残す。位置まで残すのは、
あとから「この誤りは意図的なひっかけか、偶然の一致か」を見分けられるようにするため。

自分のペース方式は `targetRate: 0` で呼ぶが、**N は渡す**（ひっかけを N±1 に置くのに要る）。
N個前との一致は禁じない。禁じると「いま出ているものは答えではない」と分かってしまう。

**計算モードでは効かない。** 式は毎回違う見た目になり、繰り返されるのは目に入らない「答え」だけ。
設定画面でもその旨を出している。詳しい理由は [nback-spec.md](nback-spec.md)。

履歴は成績の線をひっかけの有無で分ける（`splitByLure()`）。ブロック一覧にも列を出す。
v7 までの記録はトップレベルに `lure` を持たないので、`settings.lure` も見る。

## タップまわりで踏んだ落とし穴

**`hidden` 属性は作者スタイルに負ける。** ブラウザ標準の `[hidden] { display: none }` は
UA スタイルなので、`.countdown { display: flex }` のような作者スタイルがあると
そちらが勝ってしまう。その結果、カウントダウンの透明なオーバーレイが
`z-index: 2` で提示エリア全体に残り続け、入力パッドへのタップを全部吸い取っていた。
キーボードだけ効いていたのは、キーイベントが当たり判定を通らないため。

対策として `[hidden] { display: none !important; }` をまとめて置き、
`.countdown` には `pointer-events: none` も付けてある。

**タップの検証は当たり判定まで見ること。** `el.dispatchEvent(new PointerEvent(...))` は
要素に直接届くので、上に何か被さっていても通ってしまう。
実機で押せるかは `document.elementFromPoint(x, y)` がその要素を返すかで確かめる。

入力は `NB.bindTap()` に集約してある。`pointerdown` を主経路にしつつ、
Pointer Events が無い環境向けに `click` も拾い、直前に `pointerdown` が来ていたら
二重に数えない。押した合図は色の反転（`.pressed` と `:active`）と、
対応端末では短い振動。

## d′ について

対数線形補正つき。0%/100% でも無限大にならない代わりに、
ターゲット数と非ターゲット数が違う（6 対 16 など）ため、全押しでもちょうど 0 にはならず ±0.4 程度に出る。
これは補正の性質で、弁別できていないことは読み取れる。

## 記録の形

1行1ブロックの JSON Lines。`responseMode` で方式が分かれる。

- `realtime`: `n` は1以上。`hits` / `misses` / `falseAlarms` / `correctRejections` / `hitRate` / `faRate` / `dPrime`
- `paced`: `n` は1以上。`task` / `questions` / `correct` / `incorrect` / `accuracy` / `streak`。
  計算課題なら `channels[0].problems` に式が入る
- `calc`（v4まで）: `history.js` の `mode()` が `paced` に寄せる
- `recall`（廃止）: 読み込み時に捨てるので、履歴には届かない

`version: 1` の記録には `responseMode` がないが、当時はリアルタイム判定しかなかったので
履歴側でそう解釈している。

履歴画面は**方式ごとに区切って描く**。指標が別物なので同じ図に重ねると読めないし、
横軸を共有すると片方の記録の位置にもう片方の穴が空くだけで、推移としても嘘になる。
**自分のペース方式は課題ごとにさらに分ける**（位置と計算を重ねても読めない）。
区切りの単位は `history.js` の `sectionKey()`。

ブロック一覧だけは集計ではなく時系列の記録そのものなので、方式で切らずに1つの表にしてある。

古い記録や値が欠けた記録があっても壊れないようにしてある。欠けた点はグラフに打たず、
目盛の上限計算からも外す（`NaN` を座標にすると SVG が壊れてコンソールにエラーが出る）。

## 操作

回答はすべて **画面下部** に置いてある。片手持ちの親指が届く範囲。
リアルタイム判定はタップとキーの両方、自分のペース方式はタップのみ。
チャンネルが2本（デュアル）になれば、同じ場所に左右2つ並ぶ。

- リアルタイム方式: 下の大きな「一致」ボタンをタップ、またはスペースキー。一致しないときは押さない
- 自分のペース方式: 下の入力だけ（計算・数字は 0〜9、位置は3×3グリッド、混合は両方を左右に）。
  キーボードは使わない。
  最初の N 問は「次へ」。時間制限なし。
  「1つ戻る」は付けていない（前の刺激を出し直すと課題の性質が変わるため）
- 同一試行内の二重押しは無視
- ブロック中の中止 = 中止ボタン または Esc（記録は残らない）
- 履歴の「再挑戦」= 同じシードと設定で同じ列をもう一度
- ブロック中は Wake Lock で画面を消灯させない（対応ブラウザのみ）
